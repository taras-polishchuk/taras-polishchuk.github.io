The architectural decision flow

Replace "what technology" with this sequence:

  1. 1Problem — what are we solving?
  2. 2Desired outcome — what does success look like?
  3. 3Functional requirements — what must the system do?
  4. 4Non-functional requirements — how well? (latency, availability, security, cost)
  5. 5Constraints — what cannot be exceeded?
  6. 6Failure model — how can this fail? blast radius?
  7. 7Candidate options — what could solve it?
  8. 8Trade-offs — what do we gain, what do we lose?
  9. 9Decision — pick one. Write it down (ADR).
  10. 10Recovery — rollback, RTO, RPO.
Pattern

Designing your personal agent

Pattern for any agent you build — including one that operates on YOUR systems.

Capabilities

Narrowest that works.

  • Read: logs, docs, calendar (low).
  • Write: draft only, never send. (medium)
  • Execute: with explicit confirmation per action. (high)
  • Deploy: NEVER autonomous. (critical)

Tools

Narrow scopes.

  • Use OAuth scopes, not wildcards.
  • One tool per job. Don't bundle.
  • Names of tools should be obvious.

Memory

Separate from tools.

  • Long-term memory: explicit store, encrypted.
  • Short-term: conversation buffer.
  • Don't merge memory with secrets.

Failure

Designed for, not avoided.

  • LLM hallucinates a tool call → validate against schema.
  • LLM misses a step → force checklist tool before "done".
  • It loops forever → max iterations + cost cap.

Audit trail

Everything you need to debug.

  • Log every tool call (input, output, decision).
  • Log every human-in-the-loop confirmation.
  • Daily summary to Telegram.

Candidates

Dograh is one candidate, not the answer. Compare: Dograh · Retell · Bland · self-hosted Pipecat · self-hosted LiveKit.

Decision framework: per requirement, mark each candidate's fit + evidence + tradeoff. Then decide.

Topology

Coolify topology decision

Before selecting topology, identify the problem.

Possible problems

  • Centralized deployment — one place to deploy all services.
  • High availability — survives single node failure.
  • Failover — automatic switch on failure.
  • Disaster recovery — recover from catastrophic loss.
  • Remote orchestration — control multiple nodes.
  • Scaling — add capacity.

Each problem leads to a different topology. Single Coolify instance solves "centralized deployment". HA needs a cluster. DR needs off-host backup. Scaling needs an orchestrator (Kubernetes, not Coolify).

Problem → failure model → requirements → options → trade-offs → decision. Always in that order.

Anti-patterns

Beginner mistakes

Architecturally weak phrases — and the sharper version of each.

Weak phraseWhy it's weakBetter questionBetter response
"Let's use Kubernetes."Solves a problem you don't have."What failure mode are we solving?""If the answer is 'HA + scaling', we don't need it yet. Single Coolify + backups is enough."
"Let's just use Dograh."Vendor-first."What are the voice requirements?""List requirements, then compare candidates with evidence."
"Let's make it master/slave."Topology without problem."Centralized management? HA? DR?""Pick the simplest topology that solves the named problem."
"Let's give the agent full access."Violates least privilege."Read? Write? Delete? Which records?""Default to read-only. Add write with audit. Delete only via human approval."
"We can figure out rollback later."No rollback = no safe deploys."What is the rollback procedure?""Define before deploy. Test monthly."
"The agent works in testing, so we're good."No production evidence."How do we know it works in prod?""Eval suite, metrics, sampled traces. Run in CI."
"We don't need monitoring."Blind operation."How will we detect failure?""At minimum: error rate, latency p95. Alert thresholds."
"The junior can just ask me."Dependency, not delegation."What's the task package?""Goal + contract + acceptance criteria + escalation."
"Let's put everything in one workflow."Brittle monolith."What are the sub-workflows?""Split by concern. Each workflow has one job."
"Let's store the state in Telegram."Events ≠ state."What is the canonical store?""Pick one SoT. Telegram carries events only."

Anti-bluff

"I don't know" mode

How to respond when someone asks something you don't know yet.

Bad → Better

BadBetter
"Yes, probably.""I don't have enough evidence to make that architectural decision yet."
"I think so.""Let me capture the requirements first. Then I can give you a grounded answer."
"Sure, I know that.""I've seen it conceptually but not operated it. Let me ramp before committing."
"It depends.""It depends on three things — here they are, here's how each changes the answer."

The 6-step "I don't know yet" pattern

  1. 1Define the problem.
  2. 2Identify constraints.
  3. 3Gather evidence.
  4. 4Compare options.
  5. 5Decide.
  6. 6Document (ADR).

Examples when you're tempted to bluff

  • "What's the failover time?" → "I don't know yet. Let me run a chaos test."
  • "Is this HIPAA-compliant?" → "I don't know. I'm not a legal expert. I'll loop in legal."
  • "Will Mastra work here?" → "I've read docs but not shipped. Honest ramp is 1–2 weeks. Let's time-box."
  • "What's the cost per call?" → "I don't have telemetry. Let me instrument and re-measure."
  • "Can you do this in one week?" → "I don't know without discovery. Let me scope first."
  • "Is Qdrant better than pgvector?" → "It depends on scale + languages. Let me model both."
  • "What's the RPO/RTO?" → "Undefined. Let me draft and validate."
  • "Will it scale?" → "Up to N, after that we re-architect. Let me set the threshold."
  • "What about GDPR?" → "Residency + retention + audit. I can design, but legal needs to validate."
  • "What's the right model?" → "Tier per task. Let me eval Claude / GPT / local on our set."
  • "Can we self-host?" → "We can. Cost = N hours/month ops. Confirm trade-off."
  • "Why this stack?" → "Let me write the ADR so the answer is durable."
  • "What's the rollback?" → "I haven't defined one yet. That's a blocker. Let me write it."
  • "What's the cost vs quality trade-off?" → "I have a hypothesis. Let me run an eval."
  • "Is this secure?" → "I have a checklist. Let me run it and report gaps."
